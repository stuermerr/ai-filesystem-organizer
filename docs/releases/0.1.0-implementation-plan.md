## 2. Introduce the evidence and execution schemas

Dependencies: package 1.

Version the affected schemas before changing algorithms.

### Analysis Run

- retain metadata observations independently from optional Content Identity;
- represent source observations with relative path, entry type, byte size where
  applicable, and `mtime_ns`;
- persist Content Identity once per valid source observation and reuse it;
- persist bounded duplicate/structural candidate and hashing progress so scan
  resume never rehashes established identities;
- add compact file-level Execution Evidence for streamed copies, separate from
  Plan Evidence and Recovery Journal state.

### Consolidation Plan

Each Finalized Plan Entry receives exactly one tagged Evidence variant:

- `content-identity`: algorithm, algorithm version, byte size, digest;
- `metadata-observation`: entry type, applicable byte size, `mtime_ns`;
- `layout-owned-directory`: directory path, originating Layout Revision.

Implicit parents remain derived. Fingerprints include the Evidence kind and all
variant fields. Finalization still creates an immutable complete projection.

### Execution

- add a compact Materialization Attempt record containing attempt ID, Plan ID,
  timestamps, coarse state, aggregate counters, and failure classification;
- use only `ADMITTED`, `STAGING_STARTED`, `STAGING_DURABLE`, `PUBLISHED`,
  `COMPLETE`, and attempt-terminal `FAILED`;
- version the Execution Manifest and include mode, canonical destination,
  finalized fingerprint, Attempt association, staging ownership, and staging
  root `st_dev`/`st_ino` when durable;
- do not add per-file Recovery Journal events for the new normal path;
- retain only the existing state needed by the frozen in-place engine.

Legacy replanning is supported only where old evidence deterministically
produces the new representation. Otherwise return a clear fresh-scan,
fresh-plan, or restart requirement.

Acceptance: database constraints reject incomplete or mixed Evidence variants;
fingerprints are deterministic; later Execution Evidence cannot modify a
finalized Plan or its fingerprint.

## 3. Implement proof-driven scanning and bounded lazy hashing

Dependencies: package 2.

Keep all source Evidence Discovery in `scan`:

1. inventory metadata using the existing no-follow traversal policy;
2. group regular files by byte size;
3. hash only size groups containing at least two files;
4. assign the known empty Content Identity to zero-byte files without reading
   payload;
5. generate indexed, bounded metadata-only Structural Candidates from relative
   structure, entry types, sizes, and overlap;
6. hash only files required to resolve emitted candidates;
7. apply the existing conservative Relationship Actionability only after all
   required full identities exist;
8. persist final Structural Relationship evidence and complete the Analysis
   Run.

`plan` performs no source payload reads. Candidate metadata never authorizes
omission, Exact Deduplication, or Structural Union. Work is processed in bounded
batches; there is no global cap that silently drops valid evidence.

Record inventoried files/directories, metadata candidates, evaluated pairs,
newly hashed files/bytes, identity reuse/cache hits, and maximum batch size.
Add database counters only where cheap and stable.

Acceptance: unique-size-only duplicate fixtures perform no duplicate payload
hashing; a source observation is fully hashed at most once per Analysis Run;
high-fan-out inputs do not form the complete pair matrix; resumed scans reuse
completed work; lazy analysis matches the full-reference analyzer for evaluated
cases.

## 4. Build the Linux filesystem module

Dependencies: package 1. It may be developed after package 2's schema is stable
and before materialization orchestration.

Create one Linux-specific deep module with a small interface covering:

- non-blocking descriptor-bound advisory locks;
- mandatory destination capability probes and cleanup;
- `FICLONE` attempts returning typed `cloned` or
  `explicitly-unavailable` outcomes;
- one destination-filesystem `syncfs` operation;
- atomic no-replace directory publication via `renameat2` semantics;
- precise syscall/errno translation.

Use a tested allowlist for clone-unavailable errno values. Permission, I/O,
read-only, source-instability, and unexpected failures remain errors. Do not
add a runtime dependency or generic platform abstraction. Test through the
module interface with controlled syscall fakes/adapters plus narrow Linux
integration tests.

Acceptance: required probes fail closed and clean up only their own artifacts;
no check-then-rename overwrite fallback exists; unsupported clone cases alone
fall back; `syncfs` and parent-directory durability failures are observable.

## 5. Implement locking, lightweight pre-check, and CLI admission

Dependencies: packages 2 and 4.

### Locks

- add a non-blocking Run Workspace lock for conflicting finalize, preflight,
  and materialize work within one run;
- add a persistent hidden sidecar lock in the canonical destination parent,
  deterministically named from the final destination;
- never unlink the destination lock; descriptor state alone signals activity;
- acquire locks in one documented order and release them automatically with
  descriptor lifetime;
- do not serialize unrelated Plan work.

### Lightweight internal pre-check

- repeat the scanner's complete metadata-only traversal policy;
- detect added/removed paths, type changes, relevant size/`mtime_ns` changes,
  unreadability/traversal changes, and invalidated omitted evidence;
- include materially changed/new/disappeared Skipped Entry Findings without
  building forensic history;
- perform no payload reads or digest computation;
- probe actual destination capabilities, no-overwrite behavior, names, maximum
  required file size, writability, mount read/write state, and locks;
- require worst-case full streamed-copy space plus a documented staging margin;
- allow source and destination on different filesystems; require only staging
  and final destination to share the destination filesystem.

`materialize-preflight` remains finalized-plan-only, holds both locks while it
runs the same checks, and reports point-in-time evidence. It grants no durable
authorization.

### Normal CLI admission

For a draft source-preserving Plan, interactive `materialize` displays exact
Plan ID, Layout Revision, destination, and mode, then requires a standalone
confirmation. Headless use requires `--revision REVISION --yes`; stale revision
refuses. Under lock, finalize that exact revision, rerun the internal pre-check,
and create a Materialization Attempt. A failed pre-check never reopens the Plan.

In-place does not use Draft autofinalization and retains its existing explicit
finalization and destructive acknowledgements.

Acceptance: concurrency tests cover same-run and same-destination conflicts;
different destinations remain concurrent; draft revision races refuse; expert
preflight and materialize use identical checks; instrumentation proves no
payload read during pre-check.

## 6. Replace normal separate-destination materialization

Dependencies: packages 2, 4, and 5.

### Staging and ownership

- create a plan-owned sibling partial tree on the final destination filesystem;
- persist a manifest binding Analysis Run, Plan, finalized fingerprint,
  canonical destination, mode, and Attempt;
- clearly disclose that a proven owned partial tree will be discarded;
- discard it only after renewed materialization confirmation;
- refuse missing, damaged, foreign, or ambiguous ownership without deletion.

### File execution

- for same-filesystem files, attempt native clone through the Linux module;
- fall back only on explicitly allowlisted unavailable results;
- for cross-filesystem or allowed fallback, stream payload once, validate the
  bound Metadata Observation and descriptor stability, and hash during that
  same read;
- persist the resulting digest as Execution Evidence without changing the
  Plan;
- record separate cloned/copied file and byte counters;
- preserve existing user-visible metadata semantics consistently across clone
  and stream paths.

### Durability and publication

1. build the complete tree without per-file `fsync`;
2. call destination-filesystem `syncfs` and surface failure;
3. record staging-root `st_dev` and `st_ino`, then `STAGING_DURABLE`;
4. atomically publish with no-replace semantics; any existing path conflicts;
5. `fsync` the final destination parent;
6. record `PUBLISHED`, reconcile aggregates, and record `COMPLETE`;
7. report success only after completion is durable.

If parent `fsync` fails after rename, mark the Attempt failed/needs-attention
without changing the visible destination. A renewed Attempt matches its root
identity and retries durability. Recovery from `STAGING_DURABLE` plus absent
partial and present final destination uses exact root identity, not a full tree
walk. A mismatch becomes ambiguous/manual attention. No marker enters the
user-visible tree.

Acceptance: crash injection covers every coarse transition and the windows
around `syncfs`, rename, parent `fsync`, and database commits. No incomplete
partial appears as the final destination; no existing destination is replaced;
same completed materialization may return idempotent success.

## 7. Admit and scale in-place, reporting, and progress

Dependencies: packages 2, 3, 5, and 6.

- admit explicit in-place intent with the selected executor before Analysis Run
  creation and retain an execution-time capability reprobe;
- use phase-level filesystem-before-database durability, bounded checkpoints,
  invocation-local content evidence, and targeted cleanup;
- emit coarse progress for metadata scan, proof hashing, structural work,
  revalidation, destination preparation, staging, synchronization,
  publication, and completion;
- include elapsed time and available processed/total and byte counts;
- report clone/copy counters separately;
- keep JSON on `stdout` and progress on `stderr`;
- preserve detailed errors alongside the small internal failure classification;
- update README and agent skills so the normal documented path is
  `scan -> plan -> review/customize -> materialize`, while expert commands
  remain documented separately.

Tests assert broad phase ordering and useful fields, not exact human-readable
wording.

Plan derivation loads one sorted inventory projection and shares indexed
descendant ranges across structural and conflict projection. Custom Layout uses
temporary-table occupancy validation and set-based active-state persistence,
with its expensive compilation outside the final immediate transaction and all
authoritative revision writes remaining atomic. Persisted workflow progress is
observational only.

## 8. Verification, benchmarks, and Release Candidate gates

Dependencies: packages 0-7.

### Automated correctness gates

- complete `ruff`, strict `mypy`, and `pytest` workflow;
- black-box `example_source/ -> example_output/` lifecycle;
- byte-for-byte result comparison and clean user-visible destination;
- Draft revision confirmation, stale refusal, finalization immutability;
- Metadata Snapshot drift matrix, including skipped findings;
- tagged Evidence and fingerprint constraints;
- clone allowlist and unexpected-error failures;
- cross-filesystem stream copy and same-filesystem clone/fallback;
- lock contention within one run and across runs sharing a destination;
- owned, foreign, damaged, and ambiguous staging cases;
- coarse Attempt state and retry/non-retry guidance;
- crash/durability recovery around every phase boundary;
- unchanged in-place safety/regression suite.

### Scalability and I/O gates

- generated duplicate, unique-size, structural, high-fan-out, and large-plan
  datasets;
- three-run median with files, bytes, elapsed time, I/O, hash bytes, cache
  reuse, candidate/evaluated pairs, maximum batch, checkpoint, and `fsync`
  counts where stable;
- normal preflight performs zero payload rereads;
- streamed payload is read and written at most once;
- successful native clone performs no mandatory payload read;
- expensive durability work is phase-level rather than per-file;
- reproduce the old-versus-new benchmark on the same environment and document
  the improvement without imposing a portable percentage or throughput gate.

### Smoke and artifact gates

- run a small representative external-drive correctness smoke test;
- verify cross-filesystem streamed operation and fail-fast capability errors;
- build fresh package artifacts;
- install them into a clean environment;
- run CLI help, normal fixture workflow, expert preflight, and representative
  interruption/retry smoke tests from installed artifacts;
- review the exact release file inventory and privacy-sensitive content;
- verify public documentation matches the implemented commands, guarantees,
  deferrals, and Linux-only support statement.

The verified completion of these gates creates the Release Candidate and ends
engineering scope. Pushes, history/privacy publication work, visibility change,
package publication, and the `0.1.0` tag remain behind the separate manual
Publication Gate.
