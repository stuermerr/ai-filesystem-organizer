# `0.1.0` Release Scope

> [!NOTE]
> Historical release-planning record. It preserves the accepted `0.1.0` scope
> and qualification decisions, including earlier RenameProtection terminology.
> For the shipped product and current user workflow, start with the
> [README](../../README.md) and [Architecture](../../ARCHITECTURE.md).

> Status: confirmed. Release Candidate approval freezes this contract.

`0.1.0` delivers a simple, source-preserving workflow for safely consolidating
and reorganizing a quiescent filesystem collection. It prioritizes reasonable
safety, predictable behavior, and substantially lower unnecessary I/O over
forensic verification or exact per-file resume.

## Release milestones

The **Release Candidate** is engineering-complete when implementation,
documentation, required schema handling, tests, CI, package artifacts, and
required smoke tests are verified.

The separate, manual **Publication Gate** controls approved pushes, Git-history
and privacy completion, repository visibility, package publication, and the
`0.1.0` tag. A verified Release Candidate is not yet a published release.

## Supported operating model

- Linux is the only supported and verified platform for `0.1.0`.
- Windows remains a future compatibility target and is not a release gate.
- The Selected Backup Root must remain quiescent throughout the workflow.
- Separate-destination materialization is the normal mode and never mutates
  the source.
- In-place materialization remains advanced and experimental, with its current
  stricter protection, durability, revalidation, and recovery architecture.
- There is no general pre-`1.0` compatibility promise for persisted runs,
  plans, journals, or interrupted legacy executions. Clear re-plan, fresh-run,
  or restart requirements are acceptable; source data remains protected.

## Normal workflow

The documented workflow is:

```text
scan
  -> plan
  -> review/customize
  -> materialize
```

For a draft plan, `materialize` shows the exact Layout Revision, requires a
standalone confirmation of that revision, finalizes that exact revision, runs
the lightweight internal pre-check, and materializes. `plan-finalize` and
`materialize-preflight` remain available for expert and automation use, but are
not steps in the normal documented workflow. No monolithic `run` or
`consolidate` command is added.

Headless execution of a draft requires `--revision REVISION --yes`, with an
exact match to the current revision. Interactive execution shows the Plan ID,
revision, destination, and mode before asking for separate confirmation. A
pre-check failure does not reopen a finalized plan: environmental failures may
be retried, while semantic changes require a new draft.

Draft autofinalization applies only to normal separate-destination execution.
In-place execution still requires an explicitly finalized Plan, expert
preflight, destructive acknowledgement, and exact Source Root confirmation
where applicable.

## Normal materialization guarantees

The normal source-preserving path provides reasonable-safety evidence:

- required source evidence is satisfied when bytes are actually read;
- streamed copies verify source stability and may hash while copying;
- successful native clone/reflink operations are accepted from stable source
  metadata plus successful clone and publication;
- successful filesystem copy or clone operations plus final publication are
  the normal write evidence;
- incomplete staging is never exposed as a valid final destination;
- no default full destination rehash is performed;
- undetected hardware or filesystem corruption is not claimed to be covered.

The result is built in a plan-owned partial destination and published only
after staging completes. Exact per-file recovery is not required; an owned,
incomplete staging result may be discarded and restarted.

The durability boundary is phase-level: build without per-file `fsync`, call
`syncfs` once on the destination filesystem, atomically publish, `fsync` the
final destination's parent directory, and only then report success.

Discard and restart is allowed only after renewed confirmation and a valid
manifest proving the same Analysis Run, Plan, finalized fingerprint, and final
destination. Missing, damaged, or foreign manifests cause refusal without
deletion. Published destinations are never removed automatically. Publication
uses Linux atomic no-replace semantics; any existing destination path is a
conflict, and no check-then-rename overwrite fallback is allowed.

Persisted execution state is limited to `ADMITTED`, `STAGING_STARTED`,
`STAGING_DURABLE`, `PUBLISHED`, `COMPLETE`, and terminal `FAILED` with an
actionable reason. There are no per-file recovery events. Live progress remains
on `stderr`; persisted results contain aggregate clone/copy counts and bytes
plus the final outcome.

Before publication, the durable Execution Manifest records the staging root's
Linux `st_dev` and `st_ino`. If recovery finds `STAGING_DURABLE`, no partial
tree, and a final destination with the same root identity, publication is
proven and reconciliation advances to `COMPLETE`. A mismatch becomes
`FAILED`/needs-attention without modifying the destination. No internal marker
is placed in the user-visible result.

The coarse states belong to a Materialization Attempt. Every confirmed
invocation records an attempt ID, timestamps, aggregate counters, state, and a
concise failure classification. `FAILED` is terminal for that Attempt, not for
the immutable Plan; retryable environmental failures permit a newly confirmed
Attempt, while semantic and integrity failures may require a new Plan or
manual resolution.

## Proof-driven Content Identity

A full Content Identity is computed when proof requires it, not merely because
a file was inventoried:

- Exact Duplicate Groups require full identities before omission or Canonical
  Copy selection.
- Files used to prove Structural Relationships require full identities before
  the relationship is accepted.
- A unique file that is only preserved or placed may bind stable metadata to
  the plan without a pre-materialization digest. That evidence includes its
  relative path, entry type, byte size, and `mtime_ns`.
- Streamed copying computes a digest as execution evidence.
- Successful native cloning does not trigger a full read solely to create a
  digest.

A newly computed streamed-copy digest is persisted as compact file-level
Execution Evidence outside the Recovery Journal. It does not modify the Plan
or fingerprint and may be reused only while the bound source observation is
still valid. Native cloning establishes no new digest.

Every Finalized Plan Entry has exactly one tagged Evidence variant:

- `content-identity`: algorithm, algorithm version, byte size, and digest;
- `metadata-observation`: entry type, applicable byte size, and `mtime_ns`;
- `layout-owned-directory`: directory path and originating Layout Revision.

The kind and complete fields participate in the Plan fingerprint. Later
Execution Evidence never mutates the variant or fingerprint. Implicit parent
directories are derived structure and have no standalone Evidence entry.

Exact Duplicate discovery hashes only byte-size groups containing at least two
files; zero-byte files receive the known empty Content Identity without a
payload read. Structural discovery first emits indexed, bounded metadata-only
candidates, then hashes only files required to resolve them. Candidate metadata
never authorizes omission, Exact Deduplication, or a Structural Union. A full
identity established once in an Analysis Run is persisted and reused.

All source Evidence Discovery remains inside `scan`; `plan` consumes only a
completed Analysis Run and performs no payload reads. Resumed scans reuse
persisted Content Identities and bounded candidate/hash progress.

Descriptor-based checks establish stability during a concrete streamed read;
device and inode are not long-term plan identity. The model accepts the stated
non-adversarial risk of same-size replacement with a deliberately restored
timestamp.

## Required pipeline work

- make the public workflow use revision-bound confirmation and internal
  lightweight pre-checking;
- remove normal preflight content rehashing while retaining cheap source,
  destination, overlap, filesystem, capacity, and no-overwrite checks;
- perform one complete Metadata Snapshot Revalidation that detects added,
  removed, type-changed, size/mtime-changed, unreadable, and non-traversable
  entries without reading payload bytes;
- stage and publish a complete separate-destination result with coarse or
  batched durability rather than expensive per-file durability;
- use native reflink/copy-on-write cloning automatically when supported, with
  an optimized normal-copy fallback and no default hard-link optimization;
- introduce selective/lazy hashing governed by proof needs;
- fail early for known unsupported storage configurations;
- prevent conflicting preflight/materialization operations with a small,
  robust two-lock mechanism: a Run Workspace lock and a canonical-destination
  lock, both non-blocking and descriptor-bound;
- enforce standalone confirmation after the latest layout change;
- report phase, processed/total counts, bytes, and elapsed time for otherwise
  opaque long-running work.

Native cloning uses a platform-specific, tested allowlist of exact errors that
mean cloning is unavailable. Only those errors fall back to streamed copy;
permission, I/O, read-only, source-instability, corruption-like, and unexpected
failures remain visible. Reports separate native-cloned and streamed-copy file
and byte counts.

Admission is capability-based rather than a filesystem-name allowlist. Source
and destination may be on different filesystems; that skips native cloning and
uses streamed copy. Only the partial tree and final destination must share the
destination filesystem for atomic publication.

The destination lock uses a persistent hidden sidecar in the canonical
destination parent. Its deterministic name derives from that destination; it
is never unlinked after use, does not count as destination occupancy, and uses
descriptor/advisory state as the sole activity signal.

Linux-specific behavior lives behind a dedicated small module responsible for
descriptor locks, capability probes, typed native-clone attempts, `syncfs`,
atomic no-replace publication, syscall/errno handling, and probe cleanup.
Workflow, Plan semantics, Attempts, state transitions, and user-facing errors
remain in materialization orchestration. No runtime dependency or artificial
cross-platform abstraction is added.

The expert `materialize-preflight` accepts finalized Plans only, holds both
required locks while running the same lightweight checks, and returns a
point-in-time report. It provides no durable authorization; `materialize`
always repeats the internal pre-check.

Progress uses coarse internal phases covering scan, proof hashing, structural
analysis, metadata revalidation, destination preparation, staging,
synchronization, publication, and completion. Tests assert emission, broad
ordering, elapsed time, available counts/bytes, and separate clone/copy
counters without treating exact human-readable wording as compatibility.

Attempts retain a small internal failure classification for recommended next
actions: retryable environment, unsupported capability, source drift, invalid
Plan, destination conflict, I/O/integrity manual attention, ambiguous recovery,
or internal failure. Detailed errors remain separate, no class triggers
automatic mutation, and the labels are not a broad public compatibility
interface.

## Verification and performance acceptance

Normal automated tests use `example_source/` and compare against
`example_output/`. Large-scale behavior uses synthetic/generated data. A
private or very large real corpus is neither a routine test input nor a release
gate.

Acceptance requires:

- normal preflight performs no full file-content reread;
- streamed copy reads and writes payload bytes at most once;
- successful native cloning performs no mandatory full payload read;
- expensive durability/checkpoint work is not performed once per file;
- incomplete staging cannot appear as the final destination;
- synthetic benchmarks record a three-run median plus file count, byte count,
  elapsed time, I/O, and relevant checkpoint/`fsync` counts;
- one reproducible old-versus-new benchmark on the same environment
  demonstrates the improvement;
- a small external-drive smoke test verifies correctness, not throughput.

No fixed percentage improvement, elapsed-time limit, or MB/s value is a
portable release gate.

Candidate benchmarks also record inventoried files/directories, metadata
Structural Candidates, evaluated pairs, newly hashed files/bytes, reused
identities/cache hits, and maximum batch size. Tests cover zero duplicate
hashing for unique-size-only data, at-most-once hashing per run, no complete
high-fanout pair matrix, bounded batching, and equivalence with full-reference
analysis for evaluated cases.

## Explicit deferrals

The following are not `0.1.0` release blockers:

- resumable full preflight or exact per-file restart for the normal path;
- comprehensive persisted preflight history;
- heartbeat, PID, Boot-ID, or distributed lease architecture;
- sophisticated ETA or blocked-kernel-I/O diagnosis;
- forensic Source Drift evidence and full destination verification;
- automatic mountpoint relocation or AppleDouble policy;
- selectable audited/fast-safe/turbo profiles;
- semantic content enrichment, embeddings, or live-folder support;
- Windows support claims or Windows CI;
- a future RenameProtection executor for filesystems without hard links;
- speculative deep module refactors without a required behavior change.

## Release Candidate criteria

The Release Candidate requires the accepted baseline, completed pipeline work,
normal CI, relevant scheduled/manual scalability coverage, exact release-file
review, fresh built and installed artifacts, required smoke tests, and this
sanitized scope contract. Publication actions remain behind the separate
Publication Gate.

## Package A amendment

In-place intent is now admitted and persisted during scan. The current
HardLinkProtection executor uses phase-level durability, bounded adaptive
checkpoints, invocation-local verified evidence, and targeted cleanup. Plan
derivation shares one indexed inventory projection; Custom Layout occupancy and
active-state persistence are set-based. All three long-running workflows expose
observational persisted progress without changing recovery authority. The
decision and compatibility boundaries are recorded in ADR 0008, and the
reproducible evidence is recorded in
`docs/benchmarks/issue-143-package-a.md`.

## Package B amendment (superseded)

This historical Package B description applied to RenameProtection v1. Its
global current-payload-proof barrier is superseded by RenameProtection v2;
ADR 0010 is authoritative for the current safety and evidence policy.

## RenameProtection v2 amendment

RenameProtection v2 supersedes v1's global current-payload-proof barrier with a
metadata-first, component-wise executor. Its additive manifest records explicit
operations, Exact Duplicate Group membership, concrete dependency edges,
attempt-specific staging ownership, durable operation states, attention
evidence, and payload-read telemetry. Normal unchanged execution performs no
fresh payload reads; only alternate duplicate promotion establishes a current
Content Identity. Local failures preserve unresolved objects and unrelated
durable progress, while ownership ambiguity, authoritative persistence failure,
lock loss, durability-barrier failure, and unlocalizable contradictions remain
global stops. ADR 0010 and the issue-151 disposable VFAT record are the binding
safety and qualification references.
